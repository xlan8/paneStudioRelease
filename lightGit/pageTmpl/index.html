Four stuck moments

What actually eats your time is these four things

What stops people isn't the error itself — it's seeing an error with no idea which way out is open. Most tools stop halfway: they throw the raw error at you, in technical wording, without saying what to click next. Light Git puts the problem on the table first, then narrows the way out to two or three buttons.

01

The update failed — it only said so, not what to do next.

After a rejected update, nobody tells you where to click next

You changed a few files locally, and a colleague changed the same ones on the remote. You hit Update and get a failure message and a few filenames — no clue whose fault it is, what happened to those files, or whether to commit, stash or undo. You search, and every answer is a command; typing it in might make things worse. So you either click Update again and again, or freeze. The work stops there.

How Light Git handles it

It checks first: which files were changed both locally and remotely, listed one by one with the reason stated plainly — this is why the update failed. Then it gives three ways out: commit, stash or discard, each with its consequence spelled out; discarding asks for a second confirmation, so a slip of the hand won't cost you anything. After that paragraph, the next button to click is obvious.

02

You wiped your colleague's changes without a second thought.

After an update or merge, the Staged list fills up with files you never wrote — they came in with the update, from colleagues. The more you look, the more wrong it feels: not one of these is yours. Did the last operation break something? So you hit Restore, the list is clean again, and you feel fine. Then you commit and push — and everyone else's work is gone.

How Light Git handles it

During a conflict the Staged list is read-only — there's nothing for Restore or Discard to act on. Spreadsheet files (.xlsx / .xls / .csv) can't be picked hunk by hunk like text, so the conflict card shows cell-level differences with a switch between Mine / Theirs / Common ancestor, letting you judge which side to keep before choosing Use mine or Use theirs.

03

I created that branch ages ago — my colleague says they can't pull it.

The branch exists locally; the remote has nothing

Creating a branch locally is instant; the remote only learns about it after a push. You never made that push, and you've already been working on the new branch for two days. Your colleague can only see the main branch. By the time anyone notices, the two copies have drifted apart — and "I created it ages ago" was true the whole time.

How Light Git handles it

Creating a branch and pushing it are one action: the remote has it immediately, so your colleague can pull it right away. If the remote refuses (name taken, no permission), the local branch you just made is rolled back too — no branch that only exists on your machine. Local and remote branches sit in the same list, so you can see at a glance which is which.

04

I committed it. They say it never arrived.

The commit succeeded — but only on your machine

The local commit succeeds, the icon turns green, and you assume you're done. Your colleague pulls and still gets the old code. Half an hour of debugging later, you find your commit is still sitting on your own computer. Nothing threw an error, so nobody thought to check.

How Light Git handles it

Commit and push are one action — there's no second button to forget. A permanent "↑ 2 to push" badge in the sidebar keeps unpushed work visible. If a push fails, you're told whether the remote has new commits, you lack permission, or the network is down, and what to do next. There is no force push, so the fallback of overwriting someone else's commit doesn't exist either.

Design choices

How Light Git keeps those mistakes from happening

Other tools warn you. Light Git removes the entry point: it removes the states themselves, or merges them into one action. So the cases below aren't "less likely" — they don't exist.

×
No more "losing a colleague's changes while resolving a conflict"

The Staged list is read-only, and Restore and Discard have nowhere to land. There's no way to casually delete the files your colleague already committed.

×
No more "committed, but never pushed"

Commit and push are one action. With no second button, there's no step to forget.

×
No more "forgot to add it to the staging area"

There is no staging area in the interface. Tick a file and it's in this commit; untick it and it isn't. Changes can't be committed half-way because you forgot to add them.

×
No more "resolved the conflict, forgot to mark it"

Resolution depends only on whether conflict markers (<<<<<<<) remain in the file, not on a button being clicked. So "everything is fixed but the commit still fails" can't happen.

×
No more "force-pushing when a push fails"

When the remote has new commits, it updates first and then pushes, instead of handing you a switch that overwrites someone else's work.

×
No more "shows modified, opens up empty"

With Unity or Cocos projects, saving assets rewrites the line endings of text files, so Git marks them modified even though the diff is empty. Those stale-state files are detected and cleaned automatically and no longer appear in Changes. The judgment uses Git's own content rules, so real edits and staged content are untouched.

The rest of the time

On a normal day, work the way you're used to

When nothing is stuck, it's just a normal Git client — a few fewer buttons, but all the everyday steps are there.

Changes

Grouped by added / modified / deleted; only ticked files go into this commit. Line-by-line diffs, before/after comparison for images, and cell-by-cell diffs for spreadsheets (.xlsx / .xls / .csv) that also detect whole-row and whole-column insert/delete; sort by status, path or file type, filter by added / changed / conflict. Commit messages can be generated from the change statistics.

History

Commits have branch lanes, so you can see at a glance which branch a commit is on and where it was merged in. When history gets long, press Ctrl+F or click the magnifier in the title bar to search by commit message: matching rows and keywords highlight, Enter steps through the hits, and a counter under the box shows where you are in the loaded history. Open a commit for its file list and line-by-line diff (spreadsheets compare cell by cell too); expand the diff to fill the content area or step through files and hunks. Copy the hash, or create a branch or tag right at that commit.

Branches

Local and remote branches in one list, with the same switch / merge / delete workflow; merge prefers the latest commit on the remote. Creating a branch also pushes it; if the push fails, the local ref is rolled back.

Tags

Add a message to create an annotated tag and push it; click it to jump to that commit in History; deleting removes local and remote together, so no orphan tag is left on the server.

Stashes

Restore (recover and delete the record) and Apply (recover but keep the record) are separate; untracked files can be included. If a restore is blocked by uncommitted work, stash that work first and try again.

Repositories & environment

Clone directly from a remote URL; checking out a specific commit requires a target branch, so you never land on a detached HEAD. In Repository Properties you can add, edit and delete multiple remotes and choose which one updates and pushes; the last remaining one can't be deleted. Git is detected at startup — install it in one click if it's missing, or point to an existing git.exe.

Submodules

Lists each submodule's path, remote URL, current branch and uncommitted changes. Uninitialized ones can be initialized in one click; initialized ones open as standalone repositories via Manage. You can also create, change the URL or delete them; the deletion is committed on the Changes page.

Worktrees

Check out the same repository into several folders at once. Leave the path empty to generate one automatically; an existing branch is checked out as-is, a missing one is created from the current commit and pushed to the remote. Each worktree opens and is managed separately; delete it when done.

Interface

Light and dark themes follow Windows. UI in Simplified Chinese, Traditional Chinese, English, Japanese, German, Spanish and French, selected automatically from the system language.

Platform

Not tied to any hosting platform: GitHub, Gitee, GitLab or your own server — it uses the Git on your machine.

Limits

What it doesn't do

Half of the "doesn't happen" cases above come from removing features. So it's worth spelling out what's been removed — in case you actually need them.

  • No interactive history rewriting: rebase -i, squash, editing already-pushed commits
  • No force push
  • Not a hosting, pull-request or issue-tracking tool
  • No CI, no pipelines
  • No cross-repository bulk operations: several repos can be open at once, but commit and push happen one repo at a time

These aren't omissions, they're trade-offs: every such feature adds another button that can break a project — and in those few minutes, people are most likely to follow a button blindly.

If you need full history rewriting or force push, Fork, Sourcetree or GitHub Desktop are better fits — more complete, and they expect you to already understand Git. Submodules and worktrees keep only the everyday parts: submodules can be viewed, initialized, added, have their URL changed and be deleted; worktrees can be viewed, created, opened and deleted. On the same project, experienced teammates using those tools and newcomers using Light Git don't get in each other's way.

FAQ

Before you download, a few things to confirm

Do I need Git installed first?

Light Git checks for a usable Git on your system and guides you through a one-click install if it's missing.

Will my code be uploaded to your servers?

No. Code only travels between your own computer and the remotes you configure. The app has no server of its own and needs no account. Released versions report anonymous usage statistics (interaction events, version, Windows version, approximate region); no file contents, commit messages or repository addresses are collected — see the privacy policy.

Can I only connect to GitHub?

Any Git repository works: GitHub, Gitee, GitLab, a company server or a local bare repo. It uses the Git on your machine and is not tied to a platform.

How is it different from GitHub Desktop, Sourcetree or Fork?

They aim for completeness — interactive history rewriting, force push, and the full detail of submodules and worktrees — on the assumption that you already know what Git is doing. Light Git narrows the scope, but keeps the everyday submodule and worktree actions: view, initialize / create, open and delete. Full interactive history rewriting and force push are still absent. Neither is stronger; they're for different stages.

Will it silently discard my changes?

No. Discarding changes, deleting branches and aborting a merge all ask for confirmation; there's no force push; nothing rewrites your repository in the background. The only operations that touch files are ones you click, and they ask for a second confirmation.

Using Unity / Cocos — files always show as modified but the diff is empty?

The engine rewrites line endings in text files when saving assets, so Git marks them modified even though the content didn't change. Those fake changes are now detected and cleaned automatically and no longer appear in Changes. The judgment follows Git's own content rules, so real edits are untouched.
